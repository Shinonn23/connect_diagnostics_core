# Contributing to Connect Diagnostics Core

> **Required reading for all contributors** — whether writing code by hand or using AI tools.

## Quick Start

```bash
cd apps/connect_diagnostics_core

# Install pre-commit hooks (mandatory)
pre-commit install

# Verify setup
pre-commit run --all-files
```

Pre-commit enforces:

- **ruff** — linting and formatting (Python)
- **eslint** + **prettier** — linting and formatting (JS/TS)
- **pyupgrade** — Python version targeting

## Code Style & Conventions

This project enforces conventions through [`AGENTS.md`](AGENTS.md) and the scoped
[`connect_diagnostics_core/AGENTS.md`](connect_diagnostics_core/AGENTS.md). The key points:

### Python

- **Type hints on every function** — no bare `def foo(x):`
- **Import order** — stdlib → third-party → frappe → local modules
- **No wildcard imports** — no `from frappe import *`
- **`frappe.throw()`** for user-facing errors, not `raise ValueError`
- **Hook signatures** — `(doc: Document, method: str) -> None`
- **Copyright header** on all files:
    ```python
    # Copyright (c) 2026, Siwat Sroisuwan and contributors
    # For license information, please see license.txt
    ```
- **`cast()` for narrow types** — `doc = cast(ProductRegistration, frappe.get_doc(...))`
- **`# ty: ignore` with reason** — never bare `# type: ignore`

### JavaScript

- Tabs for indentation
- `frappe.call()` for server calls — no raw `fetch` or `$.ajax`
- Keep form scripts minimal — delegate logic to Python APIs

### Architecture

| Layer         | Location                    | Purpose                                                        |
| ------------- | --------------------------- | -------------------------------------------------------------- |
| API handlers  | `api/<system>/<doctype>.py` | Whitelisted methods + hook functions                           |
| DocTypes      | `cd_stock/doctype/`         | Code-managed custom DocTypes                                   |
| Custom fields | `cd_stock/custom/*.json`    | Field additions to standard DocTypes                           |
| Commands      | `commands/`                 | Custom `bench` CLI commands                                    |
| Tests         | `tests/` or co-located      | `UnitTestCase` / `IntegrationTestCase` suites (`frappe.tests`) |

### Generated Files

- `# begin/end: auto-generated types` blocks — managed by Frappe
- Module-level `__init__.py` — generated by Frappe

App-owned `doctype/**/*.json` files may be edited directly. Keep their schema,
controller, tests, and migrations consistent.

## Branch & PR Rules

### Branch naming

Use conventional prefixes with descriptive scope:

```
feature/employee-autoname-thai-year
fix/duplicate-registration-validation
hotfix/ci-broken-lint
refactor/api-module-organization
config/ai
```

### Commit messages

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
feat: add product registration validation
fix: correct Thai year calculation in autoname
refactor: simplify employment type format check
test: add employee autoname workflow tests
chore: update CI to run on developments branch
```

### PR rules

- **One feature = one branch = one PR** — no mixing unrelated changes
- **Target `developments`** — never `production` or `user-acceptance-testing`
- **CI must pass** before merge
- **No force push** to shared branches (`production`, `user-acceptance-testing`, `developments`)
- **No `--no-verify`** — pre-commit gates are non-negotiable

### Code review expectations

Every PR should:

- Pass all pre-commit and CI checks
- Include tests for new functionality
- Not modify generated Python type blocks or module-level `__init__.py` files
- Follow the type hint and import conventions above
- Have a clear Summary / Changes in the PR body

## Versioning

Version is tracked in `connect_diagnostics_core/__init__.py` as `__version__`.

**Scheme**: SemVer `0.MINOR.PATCH`, managed by Release Please from Conventional
Commits merged into `developments`.

| Commit type                                                                                 | Bump                    | Example           |
| ------------------------------------------------------------------------------------------- | ----------------------- | ----------------- |
| `feat:` / `feat(...)`                                                                       | `+1 MINOR`, PATCH → `0` | `0.7.1` → `0.8.0` |
| `fix:` / `refactor:` / `chore:` / `style:` / `test:` / `docs:` / `perf:` / `build:` / `ci:` | `+1 PATCH`              | `0.7.0` → `0.7.1` |
| Breaking change while `<1.0.0`                                                              | `+1 MINOR`, PATCH → `0` | `0.7.1` → `0.8.0` |
| `revert:` / unrecognized                                                                    | No inferred bump        | —                 |

**Rules:**

- Do not edit `__version__`, `.release-please-manifest.json`, or `CHANGELOG.md`
  manually; Release Please changes them together in its cumulative Release PR.
- Merge the Release PR when the DEV batch is ready and before promotion to UAT.
  Merging it publishes the `vX.Y.Z` tag and GitHub Release.
- The repository Actions secret `RELEASE_PLEASE_TOKEN` must have Contents,
  Pull requests, and Issues write access so the bot PR triggers required checks
  and its lifecycle labels can be maintained.
- For a revert that requires an inverse version, add `Release-As: X.Y.Z` to the
  Conventional Commit body instead of editing version files.
- The generated `release-please--*` branch is the only exception to the normal
  work-branch naming rule.
- MAJOR stays `0` until the project owner declares the app production-stable

## AI-Assisted Development

> This section defines the mandatory workflow for using AI tools. AI-generated code must meet
> the **same quality bar** as hand-written code. No exceptions.

### Why this matters

- **AI is a contributor, not an exception** — all code passes the same gates regardless of who (or what) wrote it
- **Consistency over speed** — fast code that breaks conventions creates more work in code review
- **Automated enforcement** — quality gates are enforced by tools, not by trust

### Setup (mandatory before first use)

```bash
# 1. Pre-commit hooks
cd apps/connect_diagnostics_core
pre-commit install

# 2. Codex CLI — use the repository's trusted `.codex/` configuration
# 3. Always launch from this directory
codex
```

**Read `AGENTS.md` before your first session.** It defines repository conventions, patterns, and
hard rules; `connect_diagnostics_core/AGENTS.md` adds the Frappe rules for app code. Codex reads
the trusted `.codex/` project configuration, hooks, and command rules automatically.

> Opening Codex from a parent directory (e.g. `apps/` or the Bench root) means the agent may not
> find project-specific commands and rules. Always `cd` into `connect_diagnostics_core` first.

The Notion task-tracker skills are intentionally unsupported in Codex and are not part of this
repository. Track work through the repository workflow and GitHub references instead.

### Workflow: PLAN → BUILD → TEST → SHIP

Every feature follows this pipeline. No shortcuts.

```
 ┌─────────┐     ┌─────────┐     ┌──────────┐     ┌──────────┐
 │  PLAN   │────▶│  BUILD  │────▶│   TEST   │────▶│   SHIP   │
 │         │     │         │     │          │     │          │
 │ Discuss │     │ Scaffold│     │ Verify   │     │ Quality  │
 │ Approve │     │ or code │     │ on bench │     │ gate+PR  │
 └─────────┘     └─────────┘     └──────────┘     └──────────┘
```

**Phase 1 — PLAN**

|        |                                                                                           |
| ------ | ----------------------------------------------------------------------------------------- |
| Entry  | You have a feature idea, bug report, or change request                                    |
| Action | Describe the task. AI explores the codebase, finds existing patterns, and proposes a plan |
| Exit   | You approve the plan                                                                      |

- Never skip this phase. AI without context produces inconsistent code.
- Review the proposed file list. If the AI wants to touch files outside the feature scope, push back.
- If the AI asks a clarification question, answer it — don't say "just figure it out."

**Phase 2 — BUILD**

|        |                          |
| ------ | ------------------------ |
| Entry  | Plan is approved         |
| Action | Scaffold or write code   |
| Exit   | Code passes `ruff check` |

Describe the change and let the assistant follow the existing patterns it found in
Phase 1 (an API file under `api/<system>/`, a hook wired in `hooks.py`, a `bench` CLI
command under `commands/`, or a direct edit for a small single-function change). Reuse
existing utilities — do not create parallel implementations.

After writing code:

1. **Review it** — AI can produce plausible-looking but incorrect code. Read every line.
2. **Run formatters** — `ruff check --fix <files> && ruff format <files>`
3. **Run targeted checks** — verify the changed behavior with the appropriate automated tests

**Phase 3 — TEST**

|        |                            |
| ------ | -------------------------- |
| Entry  | Implementation is complete |
| Action | Write tests                |
| Exit   | All tests pass on bench    |

```bash
# Specific test
bench --site test_site run-tests --app connect_diagnostics_core --test test_<name>

# All tests for the app
bench --site test_site run-tests --app connect_diagnostics_core

# With coverage
bench --site test_site run-tests --app connect_diagnostics_core --coverage
```

Minimum requirements:

- One test per hook handler and one per whitelisted API method
- Edge cases: empty inputs, boundary values, Thai-specific logic (BE/CE years, tax ID checksum)
- Tests must clean up after themselves — no leftover data on the test site

**Phase 4 — SHIP**

|        |                                                            |
| ------ | ---------------------------------------------------------- |
| Entry  | Tests pass                                                 |
| Action | `/ship-pr` — opens a ready-to-merge PR into `developments` |
| Exit   | PR is open on `developments`, CI is green                  |

Before the PR opens, the gate is: `uvx --from pre-commit==4.6.1 pre-commit run --all-files`
passes and tests pass. If a gate fails, fix the issue and re-run. Do not bypass gates
(never `--no-verify`).

### Command Reference

The assistant surfaces its skills automatically; you can also invoke one directly by name:

| Command    | When to use                     | What it does                                            |
| ---------- | ------------------------------- | ------------------------------------------------------- |
| `/review`  | Before committing / on a PR     | Reviews the change for defects, security, missing tests |
| `/commit`  | Ready to commit (standalone)    | Pre-commit gate + Conventional Commit message           |
| `/pr`      | Ready to open a PR (standalone) | Pre-flight checks + PR with template                    |
| `/ship-pr` | End of feature — ready to ship  | Opens a ready-to-merge PR into `developments`           |

Run the quality gate yourself any time with
`uvx --from pre-commit==4.6.1 pre-commit run --all-files` (ruff format/check, `ty-check`,
semgrep, pip-audit).

### Hard Rules

These apply to **all code**, regardless of who or what wrote it:

| #   | Rule                                | Why                                                                                       |
| --- | ----------------------------------- | ----------------------------------------------------------------------------------------- |
| 1   | `pre-commit` is non-negotiable      | If it fails, the commit doesn't happen. Never `--no-verify`.                              |
| 2   | Every function must have type hints | Enforced by `ruff`/`ty-check` in pre-commit. No bare `def foo(x):`                        |
| 3   | Never modify generated Python files | Module `__init__.py` and `# begin/end: auto-generated types` blocks are managed by Frappe |
| 4   | No placeholder code                 | No `pass`, no `TODO`, no empty docstrings. All code must be complete and functional       |
| 5   | Tests are required                  | Every new feature needs tests unless explicitly waived in the task description            |
| 6   | One feature = one branch = one PR   | No mixing unrelated changes in one branch                                                 |
| 7   | PRs target `developments` only      | Never `production` or `user-acceptance-testing`                                           |
| 8   | AI must not guess                   | If AI says it's unsure, stop and clarify. Fabricated APIs are worse than no code          |

### What to Expect from AI

| AI will do                                       | AI will NOT do                                             |
| ------------------------------------------------ | ---------------------------------------------------------- |
| Follow conventions from `AGENTS.md`              | Guess when unsure — it will ask you instead                |
| Search for existing code before writing new code | Modify generated Python files                              |
| Generate complete, functional code               | Leave placeholders or TODOs                                |
| Ask before making architectural decisions        | Choose between valid approaches without presenting options |
| Run quality checks before committing             | Skip pre-commit or CI gates                                |
| Report bugs found during implementation          | Fix bugs outside the current task scope                    |

### Typical Sessions

**New feature:**

```
You: "Add product registration validation with Thai FDA format"
 → AI explores codebase, finds existing patterns, proposes a plan

You: (review and approve plan)
 → AI asks about edge cases — answer them

 → AI writes the API file, hooks, and tests — review the output

You: bench --site test_site run-tests --app connect_diagnostics_core

You: /ship-pr
 → AI runs the pre-commit gate + tests, then opens the PR
```

**Bug fix:**

```
You: "Product registration allows duplicate registration numbers"
 → AI finds the validation code, identifies the bug, proposes a fix

You: (approve the fix)
 → AI patches the validation logic and adds a regression test

You: /ship-pr
 → Pre-commit gate + tests → PR
```

**Quick fix + commit:**

```
You: (approve a small fix)
 → AI applies it

You: /review
 → AI reports any defects or missing tests

You: /commit
 → Pre-commit gate passes, Conventional Commit created
```
